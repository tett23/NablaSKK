# ADR 0020: ローマ字かなルールの入力キーに方向キーを使えるようにする

ステータス: 破棄

## 文脈

作業者から、設定アプリの「ローマ字」ページで、方向キーをルールの入力キー(左側)に
使いたいという要望があった(例: `f` に続けて ← を押すと何かを出す)。

今の扱いは次のとおり。

- ルールの入力キーは半角の英数記号(0x21〜0x7e)だけで、大文字は使えない
  (`KanaRule.problem`)。ルールは `kana-rule.conf` の書式で、エンジンの木
  (`RomanKanaConverter`)はバイト列をキーにしている。
- 方向キーは、キーマップで `SKK_LEFT` `SKK_RIGHT` `SKK_UP` `SKK_DOWN` の事象になる
  (`data/keymap.conf`。方向キーのほか、Ctrl-B/F/A/E と 0x1c〜0x1f も同じ事象)。
  文字(`EventId::Char`)としてはローマ字の木に入らない。
- ローマ字の入力途中(`f` や `n` が待っている状態)で方向キーを押すと、エンジンは
  待っているローマ字を捨て、方向キーをアプリへ渡す(`Engine::invoke`。本家の
  `SKKInputEngine` と同じ)。入力途中でなければ、▽ の読みの中のカーソルを動かすか、
  アプリへ渡す。

本家 AquaSKK には、ルールに方向キーを書く方法はない。NablaSKK 独自の拡張になる。

方向キーをルールのどこに置けるかで、難しさが大きく変わる。

- **先頭**: 方向キーを押すたびに、ルールの続きを待つことになる。続きが来なければ
  方向キーとしての動きを後から再現する必要があり、カーソルの移動が遅れたり狂ったりする。
- **途中**(`f←a`): `f←` まで打って続きが合わなかったとき、待っていた方向キーを
  どう扱うか(捨てる、カーソルを動かす、アプリに渡す)を決めなくてはならない。
  木は合わなかったバイトをそのまま出力するので、制御文字が確定されるおそれもある。
- **末尾だけ**(`f←`): 方向キーが来た時点で、ルールに当たるかどうかが決まる。
  当たらなければ今と同じ動きにすればよく、待つ状態が増えない。

そこで、まずは末尾だけを許す。

## 実装すること

- **ファイルの書き方**: `kana-rule.conf` の入力キーの欄では、`←` `→` `↑` `↓`
  (U+2190〜U+2193)を方向キーとして読む。例: `f←,←,←,←`。入力キーの欄だけが対象で、
  出力の欄の矢印(組み込みの `zh,←,…`)は今までどおり文字として出す。
- **エンジン**(`nablaskk-core`):
  - ルールを読むとき、入力キーの欄の `←` `→` `↑` `↓` を、キーマップでそれぞれの
    事象に当たる 0x1c、0x1d、0x1e、0x1f のバイトに置き換えて木に入れる。
  - `Engine::invoke` で、ローマ字が待っていて、待っているローマ字に方向キーのバイトを
    足した列がルールにちょうど当たるときは、そのルールで変換する(文字のキーと同じ
    経路で、▽ の読みの中でも働く)。当たらないときは今と同じく、待っているローマ字を
    捨てて方向キーを渡す。
  - ひらがな・カタカナ・半角カナのモードで働く。英数などのモードと、候補の選択中は
    今のまま。
  - 方向キーは、キーマップで `SKK_LEFT` などに割り当てたキーすべてを指す。Ctrl-B/F/A/E
    と、作業者がキーページで割り当てたキーも含む。
- **設定アプリ**(「ローマ字」ページ):
  - 入力キーの欄で `←` `→` `↑` `↓` を受け付ける。1 つで 1 キーと数える(8 キーまで)。
  - 入力キーの欄の隣に、方向キーを末尾に足すメニュー(← → ↑ ↓)を置く。入力欄で
    方向キーを押してもカーソルが動くだけなので、メニューから足す。
  - 方向キーが末尾以外にあるルール、方向キーだけのルールは、理由を示して保存しない
    (「方向キーはルールの最後にだけ置けます」)。
  - 衝突の判定(同一、衝突、確定しているルールの延長。`a←` は `a` で確定するので
    打てない)は、方向キーも 1 キーとして今までと同じに行う。
- 仕様書(5.3 節)と README(日本語と英語)に書き方と制限を書く。

## 実装しないこと

- 方向キーを入力キーの先頭や途中に置くこと。要るとわかったら、待っている方向キーの
  扱いを決める ADR を別に書く。
- 方向キー以外の特殊なキー(Shift、Ctrl、Enter、Tab、Backspace など)をルールに
  書くこと。
- ルールの出力として、方向キーを押したのと同じ動き(カーソルの移動)をさせること。
- 物理的な方向キーと Ctrl-B などを区別すること。

## テスト設計

先に書いて失敗させてから実装する。

- `trie.rs`:
  - `f←,←,←,←` を読むと、`f` + 0x1c の列が `←` に変換されること。`↑` `→` `↓` も
    それぞれ 0x1e、0x1d、0x1f になること。
  - 出力の欄の `←`(組み込みの `zh`)は文字のまま出ること。
- `session.rs`(セッションを通したテスト):
  - ルール `f←,X,X,X` を足し、ひらがなモードで `f` ← と打つと `X` が確定すること。
  - ▽ の読みの途中(`▽か` のあとに `f` ←)でも `X` が読みに入ること。
  - カタカナ・半角カナのモードでも、それぞれの欄が出ること。
  - Ctrl-B(`SKK_LEFT` に割り当てたキー)でも同じに変換されること。
  - ルールに当たらない列(`k` ←)では、今までどおり待っていた `k` が捨てられ、
    方向キーは処理されない(アプリへ渡る)こと。
  - ローマ字が待っていないときの ← は、今までどおりであること(▽ の中ではカーソルが
    動き、入力中でなければアプリへ渡る)。
  - 英数モードでは変換しないこと。
- 本家の受け入れテスト(`session_test.dat`、400 ケース)が全部通ること。
- `macos/run-tests.sh`(`KanaRule`):
  - `f←` が問題なしになり、ファイルに `f←,…` と書かれ、読み戻せること。
  - `←`、`←f`、`f←a` が「方向キーはルールの最後にだけ置けます」になること。
  - `f←←←←←←←` は 8 キーで通り、`f←←←←←←←←` は長すぎになること。
  - `a←` が確定済みルールの延長として弾かれること。
- `macos/run-ui-tests.sh`: 方向キーのメニューから ← を選ぶと、入力欄の末尾に `←` が
  足されること。
- 既存の検証(`cargo test`、`cargo clippy --all-targets`、`sh swift/run-smoke-test.sh`、
  `sh macos/run-tests.sh`、`sh macos/run-ui-tests.sh`、`sh macos/build-app.sh`、
  `sh macos/check-bundle.sh`)が通ること。
- 実機で作業者が確かめる: 設定アプリで `f←` のルールを足し、テキストエディタで
  ひらがなモードのまま `f` ← と打つと出力が入り、`k` ← ではカーソルが動くこと。

## トレードオフ

- 方向キーを末尾だけに限るので、`f←a` のようなルールは書けない。その代わり、方向キーを
  押したときに待つ状態が増えず、ルールに当たらないときの動きは今と変わらない。
- ファイルの中では方向キーを矢印の文字で書く。読みやすく、手で編集もできるが、
  入力キーの欄に矢印の文字そのものを入れるルールは書けなくなる(今も入力キーは半角の
  英数記号だけなので、失うものはない)。
- 「方向キー」は事象(`SKK_LEFT` など)で決めるので、Ctrl-B などでもルールが働く。
  物理的なキーで区別すると、キーマップの外で方向キーを特別扱いすることになり、
  本家のキーマップの考え方から外れる。Emacs 風に Ctrl-B でカーソルを動かす人は、
  ローマ字の途中で Ctrl-B を押すとルールが働く点に注意が要る。
- 入力欄で方向キーを押してもキーとして入らない(カーソルが動く)ので、メニューから
  足す。キーを押して記録する専用の欄を作るほうが直感的だが、部品が増える。
