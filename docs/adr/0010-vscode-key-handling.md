# ADR 0010: VSCode でひらがなの確定と消費したキーがキーのまま届く不具合を直す

ステータス: 採択

## 文脈

VSCode のターミナルで、`l` で ASCII にしてから Ctrl-J を押し、`a` を打つと、`あ` で
はなく `a` が入る。作業者から「Ctrl-J でひらがなに戻らない」と報告があった。手元の
VSCode のターミナルは起動時に tmux を起動する。また、エディタで Vim 拡張の挿入モード
のときに Ctrl-J を押すと、不可視の文字が入っているかもしれない、という報告もある。

診断ログ(`debug.log`、2026-10-21 11:02〜11:04)から分かること:

- Ctrl-J は `key=0x6a mods=4`(`j` + Ctrl)として届き、エンジンはひらがなに切り替えて
  いる(`handled=true`、後の `mode=hirakana`)。Ctrl-J の扱い自体は正しい。
- その後の `a` は、3 回ともひらがなモードで処理され、IME は `あ` を確定している
  (`produced=true mode=hirakana`)。それでも端末には `a` が入り、作業者は Backspace で
  消している。
- `l`(ASCII への切り替え。IME は文字を出さずに消費する)の直後にも Backspace が 2 回
  あり、端末に `l` が入ったと考えられる。

仮説(どれも実機で確かめる。[テスト設計](#テスト設計)を参照):

- **仮説 1(ターミナル)**: Chromium は、キーの処理の前後どちらにもマークテキストが
  なく、確定した文字が 1 文字以下のとき、元の keydown(`key` は `a`)をそのままページへ
  渡す(5ceecf7 のコミットメッセージにも同じ記述がある)。xterm.js は keydown の `key`
  を端末へ送り、IME が確定した `あ` を使わない。そのため、1 キーで 1 文字を確定する
  ひらがなの入力も、何も出さずに消費した `l` も、キーのまま端末に入る。▽ や ▼ の
  あいだはマークテキストがあるので起きない。今の対策(`ClientQuirks`)は Chromium 系
  では Ctrl 付きのキーしか対象にしていないので、この 2 つは漏れている。
- **仮説 2(エディタ)**: 今の対策は、キーの処理を抜ける時点でゼロ幅スペース(U+200B)
  をマークテキストとして置き、少し後に `setMarkedText("")` で消す。VSCode のエディタ
  (Monaco)と Vim 拡張の組み合わせでは、このゼロ幅スペースが消えずに確定している
  可能性がある。Ctrl-J は Ctrl 付きのキーなので、今の対策の対象になる。
- **tmux**: xterm.js が `a` と `あ` のどちらを送るかは、tmux にバイト列が届く前に
  決まる。そのため tmux が原因とは考えにくいが、tmux を使わない端末でも確かめる。

このため、今の対策をそのまま Chromium 系のすべてのキーに広げるのは危険である。
Chromium 系のアプリはほかにも Claude、Chrome、Obsidian などがあり、どれも普段使って
いる。変更の範囲は VSCode に絞る。

## 実装すること

- `ClientQuirks.KeyLeak` に VSCode 用の扱いを足し、VSCode の bundle id
  (`com.microsoft.VSCode`、`com.microsoft.VSCodeInsiders`、`com.vscodium`)に割り当てる。
  ほかの Chromium 系のアプリは今の扱い(Ctrl 付きのキーだけ)のままにする。
- VSCode では、キーの処理の前にマークテキストがなく、処理の後にも残らないキーを、
  すべて Chromium から隠す。
  - **確定した文字があるとき**(ひらがなの `a` → `あ` など): 確定する文字をそのまま
    マークテキストとして置いてからキーの処理を抜け、少し後(`DispatchQueue.main.async`)
    にその文字を確定する。ゼロ幅スペースは使わない。ふつうの IME と同じく「入力中
    → 確定」の順になるので、エディタでも余計な文字は残らない。
  - **何も出さずに消費したとき**(`l`、Ctrl-J など): 今と同じくゼロ幅スペースを
    マークテキストとして置く。ただし、後で消すときに `setMarkedText("")` ではなく
    `insertText("")` でマークテキストを空の文字列で置き換え、入力中の状態をはっきり
    終わらせる。仮説 2 が正しければ、これでゼロ幅スペースが残らなくなる。
  - 後の処理を待つあいだに次のキーが来た場合は、そのキーの処理より先に、待っている
    確定を済ませる(文字の順番が入れ替わらないようにする)。
- 判断(どのキーを隠すか、どの方法で隠すか)は `ClientQuirks` の関数にまとめ、
  `macos/run-tests.sh` で検査する。
- 仕様書と README の「IME が消費したキーへの対策」の記述を、VSCode の扱いに合わせて
  直す。

## 実装しないこと

- VSCode 以外の Chromium 系のアプリの扱いの変更。必要になったら別の ADR にする。
- 入力中か確定かの状態をシステムのメニューバーに出すこと(入力モードの表示は
  `docs/roadmap.md` の候補)。
- tmux の設定の変更。
- Vim 拡張そのものへの対応(Vim 拡張の Ctrl-J の割り当てなど)。

## テスト設計

先に書いて失敗させてから実装する。

- 自動テスト(`macos/run-tests.sh`):
  - VSCode の 3 つの bundle id が新しい扱いになり、Claude(`com.anthropic.claudefordesktop`)
    や Chrome などほかの Chromium 系は今の扱いのままであること。
  - VSCode では、処理の前にマークテキストがなく、後にも残らないキーを、確定あり /
    確定なしのどちらも隠すこと。
  - 確定ありのときは「確定する文字をマークテキストにしてから確定する」方法、確定
    なしのときは「ゼロ幅スペースを置いて空の文字列で置き換える」方法を選ぶこと。
  - 処理の前か後にマークテキストがあるキー(▽ のあいだなど)と、IME が処理しなかった
    キー(ASCII モードの `a` など)は、隠さないこと。
  - 今の Ghostty と Chromium 系(Ctrl 付きのキー)の判定が変わらないこと。
- 実機での確認(作業者。コミットの前):
  1. 実装の前に、仮説 2 を確かめる: VSCode のエディタで Vim 拡張の挿入モードにし、
     Ctrl-J を押してから、カーソルを左右に動かす(余計な 1 歩があれば不可視文字が
     ある)か、ファイルを保存して `od -c` などで U+200B(`342 200 213`)を探す。
  2. VSCode のターミナル(tmux あり / なしの両方): `l` で `l` が入らないこと、Ctrl-J の
     後の `a` が `あ` になること、続けて打った `aiueo` が順番どおり `あいうえお` になる
     こと、▽ からの変換と確定が今までどおりであること。
  3. VSCode のエディタ(Vim 拡張の挿入モードとふつうの入力): ひらがなの入力、`l`、
     Ctrl-J で不可視文字が残らないこと。
  4. Claude、Chrome、Obsidian、Ghostty、TextEdit で、今までどおり入力できること。
- 既存の検証(`cargo test`、`cargo clippy`、`sh swift/run-smoke-test.sh`、
  `sh macos/run-tests.sh`、`sh macos/build-app.sh`、`sh macos/check-bundle.sh`)が
  すべて通ること。

## トレードオフ

- VSCode では、ひらがなの 1 文字ごとに「入力中 → 確定」の 2 段階を踏むので、確定が
  ほんの少し遅れる(次のメインループの 1 回分)。速く打っても順番が崩れないよう、
  次のキーの前に確定を済ませる。
- 仮説はログと既存のコミットの記述に基づく推測で、Chromium と xterm.js の中身は
  確かめていない。実機で直らなければ、この ADR を破棄して調べ直す。
- 対象を bundle id で絞るので、VSCode を元にしたほかのエディタ(Cursor など)は
  対象にならない。必要になったら bundle id を足す。
- Chromium 系のすべてのアプリに広げれば同じ問題を一度に防げるが、今の対策が
  エディタで不可視文字を残している疑いがあるうちは、普段使いのアプリに広げない。
